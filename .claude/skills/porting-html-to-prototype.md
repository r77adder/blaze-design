# Porting an HTML mockup to a real prototype

The killer workflow. The user gives you an HTML mockup (often generated by Figma Make); you turn it into a real prototype that uses lib components, surfaces gaps, and matches the design system.

## Required input

Absolute path to a `.html` file. If the user didn't provide one, ask. Examples:
- `/Users/kevinaleman/dev/Blaze H2 Features/campaigns.html`
- `/Users/me/Downloads/inbox-v3.html`

## The workflow — do every step in order

### Step 1: Read the source HTML

Read the entire file. If it's huge (>2000 lines), Read in chunks (with `offset` + `limit`) and build up a mental model.

Look for:
- `<style>` blocks — the colors, fonts, spacing the designer used
- Repeated structural patterns — sidebars, top bars, list items, cards
- Text content — headings, labels, microcopy (preserve this verbatim)
- State indicators — multiple `.html` files often = multiple states of one flow

### Step 2: Inventory components

List every distinct visual element type you see. Be specific:

```
- Sidebar with logo + nav items
- Top bar with title + 2 buttons
- Status pill (8 colors visible)
- Asset card (128x128, with hover overlay)
- Tab strip (horizontal underlined tabs)
- List item: thumbnail + 2 lines of text + status pill + action button
- Modal with header + body + footer
```

Don't skip anything. The inventory drives everything else.

### Step 3: Match each component to the lib

For each item in your inventory, check `src/components/`:

```bash
ls src/components/
grep -r "export const " src/components/ | grep -v "test\|stories"
```

Match by visual + behavioral characteristics, not by name. A "tag" in the HTML might be the lib's `Pill`. A "label" might be `Text size="xs"`.

For each inventory item, classify as:
- **Match** — exists in lib, use it
- **Close match** — lib has something similar; flag for user review
- **Missing** — must go to `GAPS.md`

### Step 4: Extract structural skeleton

Identify the high-level page structure:

```
[ Sidebar ][ Topbar  ][ ...content... ]
                     [                ]
```

Discard duplicated structure that `<PrototypeShell>` already provides (sidebar, topbar). Keep the content area structure. The shell gives you `title` + `topbarRight` slot — use those.

### Step 5: Identify states

If the HTML shows one state, ask the user what other states exist (loading, empty, error, success). If they provided multiple HTML files for the same flow, those ARE states — figure out the mapping and pass them to `<StatePicker states={[...]}>`.

Common implicit states to ask about:
- Empty (no data)
- Loading (skeleton or spinner)
- Error (failed fetch)
- Success / loaded (the happy path you usually see)

### Step 6: If porting from Blaze H2 Features, read the guidelines

If the source path is under `/Users/kevinaleman/dev/Blaze H2 Features/`, also Read `/Users/kevinaleman/dev/Blaze H2 Features/figma-make-guidelines.md` first. It documents Ivan's design intent (token names, component anatomy) — useful context for matching.

NOTE: that file says `'Söhne'` and weight 450; this repo uses `'Sohne'` (no umlaut) and maps weight 450 → 500. Translate as you port. See `CLAUDE.md` for the full mapping note.

### Step 7: Scaffold the prototype

```bash
pnpm plop prototype --name <slug>
```

Pick a slug that matches the source: `inbox-v3.html` → `inbox-v3`. Confirm with the user if ambiguous.

### Step 8: Replace scaffolded body with the real JSX tree

Edit `prototypes/<slug>/index.tsx`. Use the lib components from your inventory. The shape from `writing-a-prototype.md` applies here:

```tsx
import { Text } from '@/components';
import { PrototypeShell, StatePicker, useStateContext } from '../_shell';

function Body() {
  const { state } = useStateContext();
  return (
    <div style={{ display: 'flex', flexDirection: 'column', gap: 24, padding: 24 }}>
      {/* section: hero */}
      <Text size="lg" weight="halbfett">{/* hero text from HTML */}</Text>

      {/* section: feed */}
      {/* lib components composed here */}
    </div>
  );
}

export default function Inbox() {
  return (
    <StatePicker states={['empty', 'loading', 'loaded', 'error']} defaultState="loaded">
      <PrototypeShell title="Inbox">
        <Body />
      </PrototypeShell>
    </StatePicker>
  );
}
```

Preserve the user's microcopy verbatim. Don't paraphrase headings.

### Step 9: Log every gap to GAPS.md

For each "Missing" item from Step 3, append to `prototypes/<slug>/GAPS.md`:

```md
- **Gantt bar** — horizontal status indicator with thumbnail + label + colored left edge. Used in campaigns view. Color of left edge driven by status.
- **Status pill: New (pink)** — extension to existing StatusPill colors. Color: `var(--status-new)`.
- **Asset card** — 128x128 thumbnail with selection state (border + checkmark overlay) and hover state (darken). Used in influencer-content view.
```

Be specific: what does it look like, how is it used, what states does it have.

In the JSX, drop a clearly-marked placeholder where each missing component goes:

```tsx
<div style={{
  background: 'var(--dark-4)',
  padding: 8,
  border: '1px dashed var(--dark-15)',
  color: 'var(--dark-60)',
  fontFamily: "'Sohne', sans-serif",
  fontSize: 12,
}}>
  TODO: Gantt bar
</div>
```

The placeholder should be visually distinct so the user can scan the prototype and see what's stubbed.

### Step 10: Strip token / font cruft from any inlined HTML

If you're inlining any HTML or copying styles, REMOVE these — they're already in our tokens, and inlining them causes drift:

- All `@font-face` declarations
- All `:root { --dark-90: ...; }` blocks (or any CSS custom property definitions)
- All absolute-path font URLs like `/Users/ivanmanolov/Downloads/Soehne/...`
- Any `font-family: 'Söhne'` overrides — the playground loads `'Sohne'` globally

The lib's tokens (`src/tokens/colors.css`, `src/tokens/typography.scss`, `src/tokens/fonts.scss`) are the source of truth. Anything pasted in that re-declares them is a bug.

### Step 11: Run dev and verify

If `pnpm dev` isn't running, start it in the background. Open `http://localhost:5173/<slug>` and visually compare against the source HTML.

Things to verify:
- Layout structure matches (sidebar, topbar, content area)
- Typography looks right (sizes, weights)
- Colors look right (use browser devtools to check the rendered hex matches token values)
- States toggle correctly via the StatePicker
- Placeholders are visible where gaps exist

### Step 12: Show the user the gap report

After verifying, show the user `GAPS.md`:

> "I ported the prototype. Here's what I couldn't find in the lib — these are placeholders in the JSX. Want me to surface these to eng so they can be added to the design system? See `prototypes/<slug>/GAPS.md`."

## Common pitfalls — avoid these

- **Don't paste raw hex.** If the HTML uses `#000000aa`, find the matching token (`var(--dark-60)` is `rgba(0,0,0,0.6)` ≈ `#00000099`). When in doubt, use the closest token and note any discrepancy.
- **Don't write CSS files.** Layout via `style={}` only.
- **Don't reinvent components.** A custom `<button style={{...big inline...}}>` violates the rules. Either use a lib component or log it to GAPS.md and use a placeholder.
- **Don't guess at states.** Ask the user.
- **Don't skip GAPS.md.** That's the entire point — it's how the design system grows from real prototype needs.
